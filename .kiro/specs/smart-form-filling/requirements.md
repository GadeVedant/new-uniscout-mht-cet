# Requirements Document

## Introduction

This feature adds a dedicated "Smart Form Filling Generator" page to the UniScout MHT-CET platform. During the CAP (Centralised Admission Process) form filling period, students must submit an ordered preference list of college-branch combinations. The order is critical — students are allotted the highest-preference college they qualify for, so a poorly ordered list can cause a student to miss a better college. This feature generates a personalised, optimally ordered preference list based on the student's percentile, category, branch preferences, budget, preferred districts, and priority mode (Branch over College vs College over Branch). The list is grouped into Safe, Target, and Dream tiers and sorted within each tier by a weighted score that balances admission probability, placement outcome, location preference, and branch preference rank. Students can copy the list as plain text for direct use during CAP form filling.

## Glossary

- **Smart_Form_Page**: The new React page component `SmartFormPage.tsx` that renders the input form and the generated preference list.
- **Form_Generator**: The frontend component responsible for collecting extended input and triggering the preference list generation API call.
- **Preference_List**: The ordered list of college-branch combinations numbered 1 to N, returned by the backend and rendered on the Smart_Form_Page.
- **Preference_Entry**: A single item in the Preference_List, representing one college-branch combination with its rank number, college name, branch, cutoff percentile, admission band, admission probability, and fees.
- **Tier**: A grouping of Preference_Entries by admission likelihood: "Safe" (admission_band is "Safe" or "Likely"), "Target" (admission_band is "Moderate"), or "Dream" (admission_band is "Risky" and cutoff percentile is within 5 percentile points above the student's percentile).
- **Weighted_Score**: A numeric score computed per Preference_Entry as `(admission_probability × 0.4) + (placement_score × 0.3) + (location_preference_score × 0.2) + (branch_preference_rank_score × 0.1)`, used to sort entries within a tier. The weights are configurable via backend environment variables and should not be treated as fixed constants.
- **Entry_Reason**: A human-readable string explaining why a Preference_Entry is ranked at its position, generated by the backend from the dominant scoring factors (e.g. "High admission probability + strong placement + matches your preferred branch"). Displayed on the frontend instead of the raw Weighted_Score.
- **Admission_Probability**: The numeric probability (0–100) that the student will be admitted to a given college-branch combination, derived from the ML prediction service as specified in the `mhtcet-cutoff-prediction` spec.
- **Admission_Band**: A categorical label derived from `admission_probability`: "Safe" (≥80%), "Likely" (50–79%), "Moderate" (20–49%), or "Risky" (<20%), as defined in the `mhtcet-cutoff-prediction` spec.
- **Placement_Score**: A normalised numeric score in [0, 1] derived from the college's `avg_package` value divided by the maximum `avg_package` among all colleges in the result set; WHEN `avg_package` is null, Placement_Score SHALL be 0.
- **Location_Preference_Score**: A numeric score in [0, 1] assigned to a Preference_Entry based on whether the college's district matches the student's preferred districts: 1.0 if the college is in a preferred district, 0.5 otherwise.
- **Branch_Preference_Rank_Score**: A numeric score in [0, 1] derived from the student's ranked branch preferences: 1.0 for the 1st-choice branch, 0.6 for the 2nd-choice branch, 0.3 for the 3rd-choice branch, and 0.0 for any branch not in the student's preference list.
- **Priority_Mode**: A toggle setting chosen by the student: "Branch over College" (branch preference rank is the primary sort key within the Safe tier) or "College over Branch" (college prestige score is the primary sort key within the Safe tier).
- **College_Prestige_Score**: The `college_prestige_score` computed by the ML Feature_Engineer as the mean cutoff percentile across all branches and categories for a given college in the most recent available year, as defined in the `mhtcet-cutoff-prediction` spec.
- **Budget_Filter**: The maximum annual fees (in LPA) the student is willing to pay; colleges with annual fees exceeding this value are excluded from the Preference_List.
- **Form_Filling_Request**: The JSON request body sent to `POST /api/form-filling/generate`, containing all extended input fields.
- **Form_Filling_Response**: The JSON response from `POST /api/form-filling/generate`, containing the ordered Preference_List grouped by tier.
- **Form_Filling_Controller**: The Node.js Express controller that handles `POST /api/form-filling/generate` requests.
- **Copy_Button**: The UI button that copies the Preference_List as plain text to the system clipboard.
- **Download_PDF_Button**: The UI button for PDF export, rendered in a disabled state with a "Coming soon" label.
- **Home_Page**: The existing React component `HomePage.tsx` that serves as the platform entry point.
- **App**: The root React component `App.tsx` that manages top-level navigation state.
- **CAP_Round**: One of the Maharashtra centralised admission rounds (I, II, III).
- **Annual_Fees**: The per-year fee figure in LPA derived from the `fees` field of a college record; WHEN the `fees` string represents a total programme cost, THE system SHALL divide by 4 to approximate annual fees.

## Requirements

### Requirement 1: Smart Form Filling Entry Point on Home Page

**User Story:** As a student, I want a dedicated "Generate Form Filling List" button on the UniScout home page, so that I can access the Smart Form Filling Generator directly without going through the standard college search flow.

#### Acceptance Criteria

1. THE Home_Page SHALL render a "Generate Form Filling List" button as a distinct entry point, visually separate from the existing "Find My Colleges" entry point.
2. WHEN the student clicks "Generate Form Filling List", THE App SHALL transition the navigation state to the Smart_Form_Page view.
3. THE App SHALL extend its navigation state to include a `'smart-form'` view alongside the existing `'home'`, `'portal'`, `'results'`, `'college-detail'`, and `'college-comparison'` views.
4. WHEN the navigation state is `'smart-form'`, THE App SHALL render only the Smart_Form_Page component and SHALL NOT simultaneously render the Home_Page, MhtCetPortal, Results_Page, College_Detail_Page, or College_Comparison_Page.
5. THE Smart_Form_Page SHALL render a "Back to Home" button that transitions the App navigation state back to `'home'` when clicked.

---

### Requirement 2: Extended Input Form

**User Story:** As a student, I want to fill in my percentile, category, ranked branch preferences, budget, preferred districts, and priority mode in a single form, so that the generator has all the information it needs to produce a personalised preference list.

#### Acceptance Criteria

1. THE Form_Generator SHALL render an input form with the following fields: percentile (numeric, 0–100), category (select: Open, SC, ST, OBC, NT, EWS, TFWS), CAP round (select: I, II, III), branch preferences (ranked 1st, 2nd, 3rd choice — each a select from the standard engineering branches list), budget (numeric, maximum annual fees in LPA), preferred districts (multi-select, up to 3 districts from the Maharashtra districts list), and priority mode (toggle: "Branch over College" or "College over Branch").
2. THE Form_Generator SHALL require percentile, category, CAP round, and at least one branch preference before enabling form submission.
3. WHEN the student selects the same branch for more than one preference rank, THE Form_Generator SHALL display an inline validation error on the duplicate field and SHALL prevent form submission until the duplicate is resolved.
4. WHEN the student selects more than 3 preferred districts, THE Form_Generator SHALL prevent the 4th selection and display an inline message "You can select up to 3 districts."
5. WHEN the student enters a percentile outside the range [0, 100], THE Form_Generator SHALL display an inline validation error "Percentile must be between 0 and 100" and SHALL prevent form submission.
6. WHEN the budget field is left empty, THE Form_Generator SHALL treat it as no budget constraint and SHALL include all colleges regardless of fees.
7. WHEN the preferred districts field is left empty, THE Form_Generator SHALL treat all districts as equally preferred and SHALL set Location_Preference_Score to 0.5 for all Preference_Entries.
8. THE Form_Generator SHALL pre-populate the CAP round field with "I" as the default value.
9. THE Form_Generator SHALL display a progress indicator showing how many required fields have been completed.

---

### Requirement 3: Preference List Generation API Endpoint

**User Story:** As a backend developer, I want a `POST /api/form-filling/generate` endpoint that accepts the extended student input and returns a fully ordered, tiered preference list, so that the frontend can display it without performing any ranking logic client-side.

#### Acceptance Criteria

1. THE Form_Filling_Controller SHALL expose a `POST /api/form-filling/generate` endpoint accepting a JSON body with fields: `percentile` (float, 0–100), `category` (string), `capRound` (string, one of "I", "II", "III"), `branchPreferences` (array of 1–3 strings, ordered by rank), `budget` (number or null), `preferredDistricts` (array of 0–3 strings), and `priorityMode` (string, one of "branch-over-college" or "college-over-branch").
2. WHEN a valid Form_Filling_Request is received, THE Form_Filling_Controller SHALL return HTTP 200 with a Form_Filling_Response containing: `preferences` (ordered array of Preference_Entry objects), `tiers` (object with keys "safe", "target", "dream" each containing the count of entries in that tier), and `metadata` (object with `totalEntries`, `generatedAt` timestamp, and `inputSummary`).
3. WHEN the request body fails schema validation (missing required fields or out-of-range values), THE Form_Filling_Controller SHALL return HTTP 422 with a structured error response listing all invalid fields.
4. THE Form_Filling_Controller SHALL call the ML service `POST /api/predict-batch` to obtain `admission_probability`, `admission_band`, `p10`, `p90`, and `confidence_label` for each candidate college-branch combination before computing Weighted_Scores.
5. WHEN the ML service is unavailable, THE Form_Filling_Controller SHALL fall back to the rule-based `percentileDifference` logic to approximate `admission_probability` and SHALL include `ml_unavailable: true` in the Form_Filling_Response metadata.
6. THE Form_Filling_Controller SHALL respond within 3 seconds (p95 latency) under normal operating conditions with the ML service available.
7. THE Form_Filling_Controller SHALL include a `Preference_Entry` for every college-branch combination that passes the Budget_Filter and has at least one branch matching the student's branch preferences, up to a configurable maximum (default 50, adjustable via `FORM_FILLING_MAX_ENTRIES` environment variable) in the Preference_List.

---

### Requirement 4: Budget Filtering

**User Story:** As a student, I want colleges that exceed my maximum annual fee budget to be excluded from the preference list, so that I only see options I can actually afford.

#### Acceptance Criteria

1. WHEN `budget` is provided in the Form_Filling_Request, THE Form_Filling_Controller SHALL exclude all college-branch combinations where Annual_Fees exceed the `budget` value from the Preference_List.
2. THE Form_Filling_Controller SHALL derive Annual_Fees by parsing the numeric value from the college's `fees` field; WHEN the `fees` string represents a total programme cost (4-year), THE Form_Filling_Controller SHALL divide by 4 to obtain the annual figure.
3. WHEN `budget` is null or absent, THE Form_Filling_Controller SHALL include all college-branch combinations regardless of fees.
4. WHEN the Budget_Filter results in zero eligible colleges, THE Form_Filling_Controller SHALL return HTTP 200 with an empty `preferences` array and SHALL include a `warning` field in the metadata with the message "No colleges found within your budget. Consider increasing your budget."
5. WHEN the Budget_Filter results in fewer than 5 eligible colleges, THE Form_Filling_Controller SHALL include a `warning` field in the metadata with the message "Only {N} colleges found within your budget. Consider increasing your budget for more options."

---

### Requirement 5: Tier Assignment

**User Story:** As a student, I want the preference list grouped into Safe, Target, and Dream tiers, so that I can understand the risk profile of each section of my list at a glance.

#### Acceptance Criteria

1. THE Form_Filling_Controller SHALL assign each Preference_Entry to exactly one tier based on its `admission_band`: entries with `admission_band` of "Safe" or "Likely" SHALL be assigned to the "Safe" tier, entries with `admission_band` of "Moderate" SHALL be assigned to the "Target" tier, and entries with `admission_band` of "Risky" SHALL be assigned to the "Dream" tier.
2. THE Form_Filling_Controller SHALL include in the "Dream" tier only entries where the college's cutoff percentile is within 5 percentile points above the student's percentile (i.e. `cutoff_percentile - student_percentile <= 5`); entries with `admission_band` of "Risky" and a cutoff more than 5 percentile points above the student's percentile SHALL be excluded from the Preference_List entirely.
3. THE Form_Filling_Controller SHALL order the Preference_List with all Safe tier entries first, followed by all Target tier entries, followed by all Dream tier entries; entries from different tiers SHALL NOT be interleaved.
4. THE Form_Filling_Controller SHALL assign sequential rank numbers (1, 2, 3, ..., N) to Preference_Entries in the final ordered list, where rank 1 is the first Safe tier entry and rank N is the last Dream tier entry.
5. WHEN a tier contains zero entries, THE Form_Filling_Controller SHALL omit that tier's section from the response rather than returning an empty array for it, and SHALL include a note in the metadata indicating which tiers are empty.

---

### Requirement 6: Within-Tier Sorting by Weighted Score

**User Story:** As a student, I want entries within each tier sorted by a weighted score that balances my admission probability, placement outcome, location preference, and branch preference rank, so that the most suitable options appear first within each tier.

#### Acceptance Criteria

1. THE Form_Filling_Controller SHALL compute a Weighted_Score for each Preference_Entry using the formula: `(admission_probability / 100 × 0.4) + (placement_score × 0.3) + (location_preference_score × 0.2) + (branch_preference_rank_score × 0.1)`.
2. THE Form_Filling_Controller SHALL compute Placement_Score as the college's `avg_package` divided by the maximum `avg_package` among all entries in the full result set (before tier assignment); WHEN `avg_package` is null for a college, Placement_Score SHALL be 0.
3. THE Form_Filling_Controller SHALL compute Location_Preference_Score as 1.0 when the college's district is in the student's `preferredDistricts` list, and 0.5 when it is not; WHEN `preferredDistricts` is empty, Location_Preference_Score SHALL be 0.5 for all entries.
4. THE Form_Filling_Controller SHALL compute Branch_Preference_Rank_Score as 1.0 for the student's 1st-choice branch, 0.6 for the 2nd-choice branch, 0.3 for the 3rd-choice branch, and 0.0 for any branch not in the student's preference list.
5. WHEN two or more entries within the same tier have identical Weighted_Scores (within a tolerance of 0.0001), THE Form_Filling_Controller SHALL break ties by sorting on `admission_probability` descending, then on `college_prestige_score` descending.
6. THE Form_Filling_Controller SHALL include the computed `weightedScore` value (rounded to 4 decimal places) in each Preference_Entry in the response for internal use; the frontend SHALL NOT display the raw numeric score to students.
7. THE Form_Filling_Controller SHALL generate an `Entry_Reason` string for each Preference_Entry by identifying the top 2 scoring factors (the two components with the highest contribution to the Weighted_Score) and composing a human-readable explanation. Examples: "High admission probability + matches your preferred branch", "Strong placement record + preferred location", "Best available option in your range". The `Entry_Reason` SHALL be included in the Preference_Entry response object.

---

### Requirement 7: Priority Mode — Safe Tier Primary Sort Override

**User Story:** As a student, I want to choose whether my branch preference or college prestige takes priority within the Safe tier, so that the list reflects what matters most to me.

#### Acceptance Criteria

1. WHEN `priorityMode` is "branch-over-college", THE Form_Filling_Controller SHALL sort Safe tier entries by `branch_preference_rank_score` descending as the primary sort key, then by Weighted_Score descending as the secondary sort key.
2. WHEN `priorityMode` is "college-over-branch", THE Form_Filling_Controller SHALL sort Safe tier entries by `college_prestige_score` descending as the primary sort key, then by Weighted_Score descending as the secondary sort key.
3. THE Priority_Mode override SHALL apply only to the Safe tier; Target and Dream tier entries SHALL always be sorted by Weighted_Score descending regardless of `priorityMode`.
4. THE Form_Filling_Response SHALL include the `priorityMode` value used in the `inputSummary` field of the metadata, so the frontend can display it to the student.

---

### Requirement 8: Preference List Display

**User Story:** As a student, I want to see the generated preference list on screen with each entry clearly showing its rank number, college name, branch, cutoff percentile, admission band, probability, and fees, so that I can review the list before copying it.

#### Acceptance Criteria

1. THE Smart_Form_Page SHALL render the Preference_List as a numbered list grouped into tier sections labelled "Safe Picks", "Target Picks", and "Dream Picks".
2. WHEN the Form_Filling_Response is received, THE Smart_Form_Page SHALL display each Preference_Entry with: rank number, college name, branch name, cutoff percentile (formatted to one decimal place), admission band label with colour coding consistent with the platform's existing palette (emerald for Safe/Likely, amber for Moderate, red for Risky), admission probability percentage, annual fees, and the `Entry_Reason` string displayed as a subtle subtitle beneath the college name (e.g. "High admission probability + matches your preferred branch"). The raw `weightedScore` number SHALL NOT be shown to students.
3. THE Smart_Form_Page SHALL apply distinct visual styling per tier section: Safe Picks SHALL use an emerald/green accent, Target Picks SHALL use an amber/orange accent, and Dream Picks SHALL use a red/rose accent.
4. WHEN the Form_Filling_Response contains `ml_unavailable: true` in the metadata, THE Smart_Form_Page SHALL display a banner stating "Predictions are based on historical cutoff data. ML-enhanced probabilities are temporarily unavailable."
5. WHEN the Form_Filling_Response contains a `warning` in the metadata, THE Smart_Form_Page SHALL display the warning message prominently above the Preference_List.
6. THE Smart_Form_Page SHALL display the total entry count and the count per tier in a summary bar above the Preference_List.
7. WHEN the Preference_List is empty (zero entries across all tiers), THE Smart_Form_Page SHALL display a message "No matching colleges found. Try adjusting your filters or increasing your budget." and SHALL NOT render an empty list.

---

### Requirement 9: Loading and Error States

**User Story:** As a student, I want clear feedback while the preference list is being generated and a helpful error message if something goes wrong, so that I am never left staring at a blank screen.

#### Acceptance Criteria

1. WHEN the Form_Generator submits the form and the API call is in progress, THE Smart_Form_Page SHALL display a loading indicator and SHALL disable the submit button to prevent duplicate submissions.
2. WHEN the API call is in progress, THE Smart_Form_Page SHALL display a message such as "Generating your personalised preference list..." to set expectations about the wait time.
3. WHEN the API call returns a non-200 response, THE Smart_Form_Page SHALL display an error message derived from the API error response and SHALL render a "Try Again" button that re-enables the form for resubmission.
4. WHEN the API call fails due to a network error, THE Smart_Form_Page SHALL display the message "Unable to connect. Please check your internet connection and try again." and SHALL render a "Try Again" button.
5. WHEN the API call succeeds, THE Smart_Form_Page SHALL scroll the viewport to the top of the Preference_List section so the student sees the results immediately.

### Requirement 10: Copy List Functionality

**User Story:** As a student, I want a "Copy List" button that copies the preference list as plain text to my clipboard, so that I can paste it directly into the CAP form filling portal or share it with a counsellor.

#### Acceptance Criteria

1. THE Smart_Form_Page SHALL render a "Copy List" button in a fixed or sticky position above the Preference_List so it is accessible without scrolling.
2. WHEN the student clicks "Copy List", THE Smart_Form_Page SHALL copy the Preference_List to the system clipboard as plain text in the following format: each entry on a new line as "{rank}. {college_name} — {branch} (Cutoff: {cutoff_percentile}, {admission_band}, Fees: {annual_fees} LPA)", with tier section headers ("=== SAFE PICKS ===", "=== TARGET PICKS ===", "=== DREAM PICKS ===") inserted before each tier's entries.
3. WHEN the clipboard write succeeds, THE Smart_Form_Page SHALL display a transient confirmation message "List copied to clipboard!" for 3 seconds and then dismiss it automatically.
4. WHEN the clipboard write fails (e.g. browser permission denied), THE Smart_Form_Page SHALL display an error message "Could not copy to clipboard. Please select and copy the list manually." and SHALL NOT silently fail.
5. THE "Copy List" button SHALL be rendered only when the Preference_List contains at least one entry; WHEN the list is empty, the button SHALL NOT be rendered.

### Requirement 11: Download PDF Button (Disabled / Coming Soon)

**User Story:** As a student, I want to see a "Download PDF" button on the page so that I know PDF export is a planned feature, even though it is not yet available.

#### Acceptance Criteria

1. THE Smart_Form_Page SHALL render a "Download PDF" button adjacent to the "Copy List" button.
2. THE "Download PDF" button SHALL be rendered in a visually disabled state (reduced opacity, non-interactive cursor) and SHALL display a "Coming soon" tooltip or label.
3. WHEN the student clicks the disabled "Download PDF" button, THE Smart_Form_Page SHALL NOT perform any action and SHALL NOT navigate away from the page.
4. THE "Download PDF" button SHALL remain visible and disabled regardless of whether the Preference_List is populated or empty.

---

### Requirement 12: Preference List Round-Trip Consistency

**User Story:** As a developer, I want the preference list generation to be deterministic for the same input, so that students get a consistent list when they regenerate with the same parameters and the system is testable.

#### Acceptance Criteria

1. THE Form_Filling_Controller SHALL produce identical Preference_List ordering for identical Form_Filling_Request inputs when the underlying ML predictions and college data have not changed.
2. FOR ALL valid Form_Filling_Request inputs, serialising the Form_Filling_Response to JSON and deserialising it SHALL produce an equivalent object with the same entry count, rank assignments, tier assignments, and Weighted_Score values (within floating-point tolerance of 0.0001).
3. THE Form_Filling_Controller SHALL include a `dataVersion` field in the Form_Filling_Response metadata indicating the version of the college dataset used, so that clients can detect when a list was generated from stale data.
4. WHEN the same Form_Filling_Request is submitted twice within the same data version, THE Form_Filling_Controller SHALL return Preference_Lists with identical rank orderings.

### Requirement 13: API Type Definitions

**User Story:** As a frontend developer, I want TypeScript interfaces for the Form_Filling_Request and Form_Filling_Response in `src/services/api.ts`, so that the compiler enforces correct usage of the new endpoint across the codebase.

#### Acceptance Criteria

1. THE `src/services/api.ts` file SHALL define a `FormFillingRequest` interface with fields: `percentile` (number), `category` (string), `capRound` (string), `branchPreferences` (string array), `budget` (number or null), `preferredDistricts` (string array), and `priorityMode` (`'branch-over-college' | 'college-over-branch'`).
2. THE `src/services/api.ts` file SHALL define a `PreferenceEntry` interface with fields: `rank` (number), `collegeName` (string), `branch` (string), `cutoffPercentile` (number), `admissionBand` (`'Safe' | 'Likely' | 'Moderate' | 'Risky'`), `admissionProbability` (number), `annualFees` (number or null), `weightedScore` (number), `entryReason` (string), `district` (string), `collegeType` (string), `tier` (`'safe' | 'target' | 'dream'`), and optional `avgPackage` (string or null).
3. THE `src/services/api.ts` file SHALL define a `FormFillingResponse` interface with fields: `preferences` (array of `PreferenceEntry`), `tiers` (object with `safe`, `target`, `dream` counts), and `metadata` (object with `totalEntries`, `generatedAt`, `inputSummary`, `dataVersion`, optional `warning`, and optional `ml_unavailable`).
4. THE `api` object in `src/services/api.ts` SHALL expose a `generateFormFillingList(request: FormFillingRequest): Promise<ApiResponse<FormFillingResponse>>` method that calls `POST /api/form-filling/generate`.
5. ALL new interfaces SHALL be exported from `src/services/api.ts` so they can be imported by `SmartFormPage.tsx` and any other components that consume the form filling API.
